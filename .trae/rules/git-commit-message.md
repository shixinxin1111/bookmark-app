# Git 提交信息规范

生成提交信息时，必须遵循以下规则。

## 输出要求

- 只输出最终提交信息，不要输出解释、分析过程或 Markdown 包裹。
- 如果只需要标题，则只输出一行提交标题。
- 如果需要正文，则输出完整提交信息，标题和正文之间保留一个空行。

## 基本要求

- 使用 Conventional Commits 风格：`<type>(<scope>): <subject>`。
- `scope` 可选；没有明确模块时省略。
- 破坏性变更可使用 `!` 标记：`<type>(<scope>)!: <subject>`。
- 提交信息必须使用中文为主，禁止生成纯英文标题。
- 提交标题应简洁说明本次改动，优先使用动宾短语。
- 提交标题控制在 72 个字符以内。
- 提交标题末尾不要添加句号。
- 不要使用含糊表达，例如：`更新代码`、`修改问题`、`优化一下`。
- 不要为了符合格式强行编造不存在的改动内容。

## type 取值

- `feat`：新增功能。
- `fix`：修复缺陷。
- `docs`：文档变更。
- `style`：不影响逻辑的格式、样式调整。
- `refactor`：不新增功能、不修复缺陷的代码重构。
- `perf`：性能优化。
- `test`：测试相关变更。
- `build`：构建、依赖、脚手架相关变更。
- `ci`：持续集成相关变更。
- `chore`：工程杂项、配置、清理类变更。
- `revert`：回滚提交。

## type 判断原则

- 新增用户可感知能力时使用 `feat`。
- 修复错误、异常或不符合预期的行为时使用 `fix`。
- 只改文档时使用 `docs`。
- 只改格式且不影响代码含义时使用 `style`。
- 调整代码结构但不改变行为时使用 `refactor`。
- 改依赖、构建脚本、打包配置时使用 `build`。
- 改 Git Hooks、编辑器配置、项目规则等工程配置时优先使用 `chore`。

## scope 规则

- `scope` 使用小写英文或项目内已有模块名。
- `scope` 应尽量简短，例如：`electron`、`react`、`lint`、`deps`、`git`。
- 不要为了凑格式强行添加 `scope`。
- 多个模块同时变更且无法确定主模块时，省略 `scope`。

## 正文规则

当改动较简单时，只生成一行标题即可。

当改动包含多项内容、破坏性变更或需要说明背景时，增加正文：

- 标题与正文之间空一行。
- 正文使用中文说明“做了什么”和“为什么做”。
- 每行尽量不超过 100 个字符。
- 如果有破坏性变更，正文中必须包含 `BREAKING CHANGE:`。
- 正文不要重复标题，应补充标题无法承载的上下文。
- 如果无法确定改动意图，优先使用更保守、具体的描述，不要泛化成“优化”或“调整”。

正文可使用简短段落或列表，但不要写无意义的套话。

## 示例

```text
feat(electron): 初始化桌面应用运行骨架
```

```text
build: 接入 ESLint 与 Prettier 配置

补充项目级代码检查和格式化脚本，统一后续开发时的代码风格。
```

```text
fix(react): 修复页面入口组件无法热更新的问题
```

```text
docs: 完善 Git 提交信息规范
```

```text
chore(git): 接入 Husky 提交工作流

使用 lint-staged 处理暂存文件，提交信息校验保持 Conventional Commits 默认规则。
```

```text
feat(storage)!: 调整本地数据存储结构

BREAKING CHANGE: 旧版本生成的数据文件需要迁移后才能继续读取。
```

## 非规范示例

```text
update code
```

```text
修改
```

```text
feat: 优化一下项目
```

```text
fix: 修复问题。
```
